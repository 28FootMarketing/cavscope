## New evidence this pass (not in the prior audit)
- **Zero real production incidents exist.** `muster.scans`: 5 rows total, ever, all `status = 'complete'`, zero `failed`/stuck rows, earliest 2026-09-04, latest 2026-09-06. The product has been live for two days. Every design decision below is necessarily proactive (built ahead of failure), not reactive to observed failure patterns — stated plainly so nothing here is misread as "learned from incidents."
- **Two real recovery playbooks already exist, undocumented, inside `muster.engine_claim()`:**
  1. Stuck-scan timeout: any scan `status='running'` for >10 minutes is marked `failed` with `error_message = 'Engine timeout: no result within 10 minutes'` on every claim cycle.
  2. Orphaned-queue pickup: a scan `status='queued'` for >2 minutes (its HTTP kick from `pg_net` presumably lost) is picked up and run directly by the next `mode:'due'` claim cycle.
  Both are real, running code, exercised every 15 minutes by `muster-scan-due` — not proposals.
