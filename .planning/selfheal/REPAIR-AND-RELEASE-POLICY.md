# REPAIR STATE MACHINE, RELEASE POLICY, AND GUARDRAILS — MUSTER

## Repair state machine (section 8)

Trigger: a `muster.incidents` row reaches `severity in ('warning','critical')` and the platform-owner alert email lands. This is a human-initiated handoff, not an autonomous one -- see ARCHITECTURE.md for why.

1. **Claim.** Anthony (or whoever is triaging) starts or resumes a Claude Code session and says "handle incident #N." The session calls `muster_admin_incidents()`, reads the target row, and calls `muster_admin_update_incident(id, 'investigating')`. This is the single-claim lock -- `status='investigating'` plus `claimed_by`/`claimed_at` prevents two sessions from independently working the same incident (checked by convention today; a future hardening is a DB-level `for update skip locked` claim RPC if concurrent triage sessions ever become real, not needed yet with one operator).
2. **Investigate.** Read the incident's `evidence` JSON, the affected function/migration's current source, `cron.job_run_details` or `muster.scans` directly for more context, and the live Supabase advisors if relevant. Classify `root_cause_classification` from the list in the incidents table -- this is a required field before proceeding, not an afterthought.
3. **If not a code defect** (expected validation, external outage, expired connection, quota limit, etc.): record the classification, take the applicable runtime action (nothing MUSTER doesn't already do automatically per the RP-01/02/03 playbooks, or a manual one-off fix like re-registering a webhook), set `recovery_result`, move to `recovered` or `closed`. No code changes, no PR. This is the direct implementation of "a signal is evidence to investigate, not permission to deploy a patch."
4. **If a code defect:** read the affected production commit (the SHA on `main` at the time the incident's evidence was captured) to understand the code that actually ran, then diff against current `main` -- if the defect is already fixed, record that and close with `wont_fix` (duplicate/already-resolved), no new patch.
5. **Reproduce.** Write a minimal committed regression test or a deterministic SQL/HTTP reproduction (MUSTER has no test framework -- see `.planning/autonomy/EVIDENCE-REGISTER.md` FIND-011 -- so "committed regression test" today means a `.sql` fixture + assertion query checked into the PR, or a documented `curl`/`pg_net` repro command, not a Jest/pytest file that doesn't exist yet). Demonstrate it fails on unpatched code.
6. **Patch.** Smallest correction at the binding layer (the RPC, the edge function, the migration -- whichever actually owns the defect). Stay inside the incident's declared scope; no drive-by refactors.
7. **Demonstrate the fix**: re-run the reproduction, show it now passes. Exercise directly related invariants (e.g., a fix to `muster.autotriage()` gets re-run against live data the same way PRD-001's change was, per this session's own established pattern).
8. **Independent verification.** Since there is no separate CI or a second automated evaluator today, this step is honestly a **second pass by a human or a fresh Claude Code session that did not write the patch**, reviewing the diff, the reproduction, and the before/after evidence -- not the same session simply re-asserting its own work. Record who verified and what they checked.
9. **Open one draft-equivalent PR** linked to the incident id in its description, with the evidence and verification notes included (mirroring this session's own PR-description conventions).
10. **Release** only per the policy below.
11. **Closure**: after Anthony merges and the fix deploys, re-check the original failing condition against production (a real query/request, not "the PR is merged so it must be fine"), update `status` to `deployed_awaiting_observation`, then `closed` after a stated observation window (proportional to the incident -- a stuck-scan-timeout tweak needs one clean cron cycle; a schema/security fix needs longer). Record `closure_evidence`.

## Release policy (section 10)

**Current, honest state:** every merge to `main` in this repo, all session, happened only after Anthony's literal words "Open PR and merge." That is a real, consistently-followed control -- but it is enforced by **instruction-following inside this conversation**, not by a GitHub branch protection rule. No tool available in this session could confirm or deny whether `main` has branch protection configured (RUN-STATE.md). **This is a real gap against section 10's explicit requirement ("enforce authorization in the repository/deployment system, not merely in an agent prompt") and is reported as a gap, not smoothed over.**

**Policy, as it stands today:**
- Zero-human production release is **not authorized**. Nothing in this session's history or this assignment's own text ("leave verified fixes as draft/reviewable PRs until the authorized reviewer approves... do not call this zero-human source deployment") changes that.
- Every repair PR stays open until Anthony explicitly approves and merges it, exactly as every PR this session has already worked.
- Eligible-for-eventual-fast-track change classes (if Anthony ever wants to revisit this): none defined yet. Excluded/high-impact surfaces that would NEVER be eligible even under a future fast-track: RLS policies, `muster_admin_*`/`muster_engine_*` grant statements, money/pricing/commercial_pricing tables, consent/marketing logic, `.github/` and branch-protection configuration, this `.planning/selfheal/` policy set itself.
- **Recommended, not enacted:** Anthony enables a GitHub branch-protection rule on `main` requiring at least one review before merge and disallowing direct pushes. This is the concrete technical control that would close the gap above. Not done in this pass -- changing repository protection is a protected-path/maintenance action under section 12A, requiring its own explicit go-ahead, not something to slip in under a self-healing PRD.
- Approvals are tied to the PR's head SHA. A new commit pushed after Anthony's "merge it" but before the merge actually happens invalidates that instruction -- re-confirm before merging if the head changed. (This has not come up yet in practice, but is a real property GitHub itself would enforce with the branch-protection rule above; without it, this session enforces it by re-checking the head SHA before every merge call, as already done for this exact PR-merge history.)

## Guardrail register / threat model (section 12A)

MUSTER's repair loop today has one real actor with elevated access: **a human-invoked Claude Code session**, using the same credentials this entire multi-week session has already used (GitHub MCP scoped to `28FootMarketing/muster`, Supabase MCP scoped to project `mgtmqucaldkaxvxglguw`). It does not yet have an autonomous webhook-triggered coding agent, so several of the assignment's threat classes are **not yet applicable** (marked NOT_APPLICABLE_WITH_EVIDENCE below) rather than defended against with invented controls for a system that doesn't exist.

| Threat | Applicable today? | Control |
|---|---|---|
| Malicious ticket/incident text expanding tool privilege | Partially -- `muster.incidents.evidence` is populated only by the watchdog's own fixed, parameterized queries (never raw user/tenant free text), so there's no untrusted-text-in-evidence path today. If a future incident source ever ingests raw user reports, they must be treated as data, never instructions, exactly as this session already treats every `<untrusted-data>`-wrapped query result. | Evidence is machine-generated aggregate data only, by construction |
| Poisoned dependency / malicious generated patch | Applicable | Every patch is human-reviewed before merge (release policy above); no auto-merge exists |
| Compromised webhook sender | Applicable to `muster-ghl-webhook`/`muster-stripe-webhook`, not to the watchdog (which has no inbound webhook -- it's cron-only, outbound-only via `muster_engine_report_incident`) | Signature verification already implemented and tested for both existing webhooks (this session) |
| Credential theft from the repair environment | Applicable | Repair sessions use the same GitHub/Supabase scoping already in force for this session -- no separate, wider credential was minted for this work. No production `service_role` key is ever given to a repair session; it works through the same MCP tools with the same scope this conversation already has. |
| Cross-client repository confusion | NOT_APPLICABLE_WITH_EVIDENCE today -- there is exactly one repository in scope (`28FootMarketing/muster`), no multi-tenant repo-mapping logic exists to confuse |
| Untrusted PR code reading deployment secrets / altering required checks | NOT_APPLICABLE_WITH_EVIDENCE today -- there is no CI that runs PR code with privileged secrets (no CI exists at all yet, per FIND-011); this is a real gap to close *when* CI is built (see `.planning/autonomy/IMPLEMENTATION-SERIES.md` PRD-004), not something to falsely claim is defended now |
| Repair agent modifying its own guardrails / budget / required checks | Applicable, and explicitly excluded in the release policy's protected-surface list above. No technical enforcement exists yet beyond "the release gate is a human," since there is no CI/required-check system for a patch to weaken. |
| Revocation / kill switch reaching queued work | Partially applicable -- there is no queue of pending autonomous repair jobs to revoke (repair is human-initiated per instance, not a running fleet). The one standing automated privileged loop is `muster-watchdog` itself: `select cron.unschedule('muster-watchdog-10min');` is the kill switch, stops new incident creation within one cycle. It does not retroactively affect a human-invoked repair session already in progress -- that session is stopped the same way any Claude Code session is stopped (by the human). |

**Residual risk, stated plainly:** this design's actual weak point is exactly the gap named in the release policy section -- there is no technical (GitHub-enforced) barrier today preventing an agent from merging without asking. The barrier is the operating instructions this session follows. That is a real control (it has held for every merge this session performed), but it is not the "enforced outside the model" control the assignment asks for, and this document does not pretend otherwise.
