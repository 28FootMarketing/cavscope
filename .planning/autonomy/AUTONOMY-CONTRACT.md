# AUTONOMY-CONTRACT — MUSTER

Scope: the autonomous actions that already exist plus the one proposed in PRD-001. This is not a general-purpose agent-authority contract (MUSTER has no free-form AI agent acting on a tenant's behalf today) — it's a record of exactly which automated writes are authorized, under what precondition, with what limit, and how to stop them.

| Action | Actor | Precondition | Scope/limit | Reversibility | Kill switch | Status |
|---|---|---|---|---|---|---|
| Auto-resolve a finding on rescan | `muster.engine_ingest` (service_role, via `muster-scan`) | scan completes, rule not triggered | one finding at a time, HTTP rules only | reversible (reopens on reappearance) | none needed — deterministic, reversible, low-risk; no incident has motivated one | VERIFIED_WORKING, already live |
| Auto-open a risk + remediation action from a finding | `muster.autotriage()` (service_role, cron every 15 min) | finding open/reopened, severity in (critical, high, medium), not yet linked to a risk | one risk per finding, org-scoped | reversible in effect (auto-mitigates on resolve); the risk record itself is not deleted, only status-transitioned — correct, since deleting a risk record would destroy audit history | none today — `organizations.critical_alerts_enabled` (PRD-001) does not gate this; it only gates the *alert*, not the risk-opening itself, since the risk record is the audit trail, not a notification | VERIFIED_WORKING, already live |
| Queue + send a critical/high risk alert email | `muster.autotriage()` queues; `muster-alert-dispatch` sends (service_role) | risk newly opened, severity critical/high, org has >=1 executive/risk_owner member, `organizations.critical_alerts_enabled = true` | one email per distinct risk, ever (unique dedupe key) | not reversible once sent (an email can't be unsent) — this is exactly the case the assignment calls out needing a defined compensating response rather than an invented undo: the compensating action is a prompt follow-up correction, not a retraction, and is out of scope for v1 | per-org: `organizations.critical_alerts_enabled = false` (self-service, immediate — takes effect on the next `autotriage` run, does not need to reach an in-flight queued row since queuing itself checks the flag); fleet-wide: `cron.unschedule('muster-alert-dispatch-5min')` stops all sending within 5 minutes | PROPOSED (PRD-001), not yet implemented |
| Provision a paying tenant from a GHL webhook call | `public.muster_ghl_provision` (service_role, via `muster-ghl-webhook`) | valid `x-muster-secret`, a human has already marked the GHL deal Closed Won | one org per call, idempotency depends on GHL not re-firing the same webhook twice (not independently verified this pass) | not reversible via software — cleanup requires the manual FK-ordered deletion procedure this session used for test-data cleanup; there is no `muster_admin_delete_org` RPC | none today beyond disabling the GHL workflow itself (external to this repo) | VERIFIED_WORKING, already live, HUMAN_DEPENDENT upstream trigger |

## What is explicitly NOT authorized by anything in this repo today
- No function in `muster.*` can change a tenant's billing plan without either a super-admin RPC call (`muster_admin_set_plan`, itself gated by `muster.is_super_admin()`) or the GHL webhook path above. There is no autonomous upsell/downgrade logic.
- No function can send a message to an end-customer of a tenant (MUSTER has no concept of a tenant's own customers — it monitors the tenant's website, it doesn't act on the tenant's behalf toward third parties). This keeps MUSTER's blast radius narrow: worst case for a bug is a wrong internal alert or risk record, not an unauthorized message sent to someone else's customer.
- No function can modify jurisdiction law content automatically — that stays human-authored, correctly (WORKFLOW-COVERAGE P-15).

## Deterministic authorization note
Every autonomous write above is gated in SQL/Postgres (RLS, `is_super_admin()`, `is_org_member()`, explicit revoke/grant), not by an LLM's judgment — there is no LLM in any of these paths today. The `muster-agent` gateway is the one component that puts an LLM client in the loop, and it is read-heavy by design (write tools are limited to `update_finding_status`/`promote_finding_to_risk`/`request_scan`, all of which are also directly callable by a human through the same RPCs with the same RLS checks — the gateway does not grant the agent any authority a human org member wouldn't already have).
